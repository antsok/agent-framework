# Adversarial review, 6 September 2026

Three reviewers were pointed at the runs 36-39 work with instructions to attack it: one at the
empirical claims, one at the code, one at the design and the conclusions. They worked from the
records and the source rather than the write-ups, and did not see each other's findings.

Everything marked **verified** was re-derived independently before being accepted. The review was
severe: the central narrative of runs 38-39 does not survive it, and several statements that
reached the user were wrong.

---

## 1. The coverage check measures the wrong thing, and can lose data -- verified

Two reviewers found this independently.

`_distinctive_tokens` splits on whitespace and strips punctuation only at the ends. The live tool
renders values as `code_1=TL-BA44A9`, so the token is the compound `code_1=tl-ba44a9`. A record
quoting the bare value -- which is what `RECALL_VALUES_DESCRIPTION` asks for -- never matches.
Replayed directly:

    tool renders    : code_2=TL-BA44A1 code_3=TL-BA44A2 code_4=TL-BA44A3
    tokens extracted: ['code_2=tl-ba44a1', 'code_3=tl-ba44a2', 'code_4=tl-ba44a3']
    a record quoting every value, bare -> coverage 0/3

**Every UNCOVERED figure in runs 38 and 39 measures whether the model copied the benchmark's label
format.** Not whether it preserved anything.

Worse, `_is_covered` tests `value in record` on lowercased text, so a group is *dropped* when its
values appear as substrings of unrelated ones:

    group values : ['2026', '1234']
    record       : "ZZ-999999 was recorded on 2026-08-31 as AB-123456"
    -> both "matched"; group DROPPED

Any 4-6 digit number is covered by any longer identifier or date containing it. The check
introduced to stop silent deletion of unrecorded data **can silently delete unrecorded data**. The
name fallback has the same defect: `record.count("get")` is satisfied by `get_status`, and
prefix-sharing tool names are the norm.

It also does not generalise, contrary to its own docstring: compact JSON is one whitespace token,
and key=value lines and CSV rows degenerate the same way. Upstream that is a strategy that never
deletes on JSON tool output.

The tests never catch it because the fixture supplies bare `AB-123456` values rather than what the
live tool emits.

## 2. The runs 38-39 mechanism does not reach the archive -- verified

Claimed: "the strategy was destroying its own record", applied to the archived luna 21/53.

The code those runs executed dropped **every** tool group before the record unconditionally, and
called the fallback only when the prompt still exceeded the ceiling. It never did:

| archived cell | peak prompt | ceiling |
| --- | ---: | ---: |
| luna 60K/0.86 | 32,138 | 57,952 |
| luna 120K/0.86 | 77,978 | 117,952 |
| luna 200K/0.86 | 130,360 | 197,952 |
| mini 120K/0.86 | 100,979 | 117,952 |

Every archived peak sits 30-45% under its ceiling. **The post-record fallback cannot have fired in
runs 26-35.** So:

- **"Runs 26-35 cannot be trusted because every row ran the unflagged fallback" is withdrawn.** It
  was a large claim about a lot of archived work and it was wrong. Those runs are the cleanest
  measurement of record-then-drop as designed.
- The archived luna 21/53 means what section 3h said: luna's record held two lookups. Section 3j
  overwrote a correct explanation with an incorrect one.
- The dumped record came from an unarchived invocation under run-38 code (schema 5, no
  `fallbacks_after_record` field), where the fallback could fire unreported. **It is not evidence
  about run 34.** Its codes appear in no archived row.

What survives: `_anchored.py` genuinely had no concept of a record, and the run-38 trim really
happened. Protection is still a correct fix. It is not the explanation of the archive.

## 3. Run 39's headline is not like-for-like and its cost half is noise -- verified

- **Different operating points.** Run-34's 60K control seeded 46,387 tokens (77% fill, itself
  flagged FILL OFF TARGET); run 39 seeded 51,191 (85%). The project's own fill caveat says such
  cells "do not sit on the same axis".
- **Half the swing is the control moving.** Control seed cost went 0.0300 -> 0.0382 (+27%). Run-39
  strategy against run-34 control is **+25%**, not -2%.
- **The noise floor swallows it.** `truncation`, untouched by any commit in between, reads
  +31, -1, +10, -1, +53, -2 across six samples of this cell. A 58-point move is indistinguishable
  from that. The instrument itself printed NOT SUPPORTED.
- **"The first row in this project to hold every fact without costing more" is false.** Run 33
  share 0.80/120K mini reads -3% at 53/53 with a clean verdict -- quoted in this same document
  thirty lines earlier. Run 34 120K/0.50 has three strategies at 53/53 with negative vs none.

## 5. Code defects -- verified

- **Every trigger event writes two records.** Reproduced in a real pipeline:
  `records_in_conversation=2` even with repeats off, because `_record_due` re-fires on the exit of
  the pinned call where the record is not yet visible. With repeats on: 4-5 records, and hijacked
  seeding turns lose their own pinned lookup because the middleware overwrites `tool_choice`. Two
  docstrings assert "one is the cost of the design". Both are wrong.
- **`_drop_before` reads only the newest record**, which is that redundant second one. A model
  writing "already recorded above" makes every group read uncovered while a complete record sits
  preserved one message earlier. Plausibly explains run 39's UNCOVERED:6 seed.
- **RECFALLBACK counts attempts, not effects** -- incremented before `await self.fallback(...)`,
  regardless of result. RECFALLBACK:5 may be five no-ops.
- **`groups_kept_uncovered` never shrinks**, so it reports groups later covered and deleted.
- **A commissioned test is vacuous**: `test_the_record_count_is_a_maximum_rather_than_a_running_total`
  still passes when `max(...)` is mutated to `+=`.
- **`repeat_records=True` was made the default on unit tests alone.** No live run has used it.

## 6. Design findings not yet acted on

- **`trigger_fraction` 0.6 -> 0.8 is unsupported and probably backwards.** No run has used 0.8. The
  project's own data say the record degrades with the bulk it must read, so a later trigger means a
  bigger ask and a worse record. The break-even argument is also inverted: an edit repays over the
  turns that follow it, and firing later leaves fewer of them.
- **Repeats are unbounded in the case that matters.** Above the trigger -- permanent once a
  preserved record is added -- every tool-call group re-arms, and the prompt asks for "everything
  from earlier tool results" rather than "since the last record", so records grow and duplicate.
- **Every luna row carries NO:temp.** `runs/README.md` voids an earlier run for being unpinned;
  luna is unpinned on temperature, has the largest spreads, and the two were never connected.
- Docstrings are benchmark war stories -- model names, token counts, "luna writes..." -- which is
  not what a framework maintainer wants to read.

## What survived all three attacks

- r = 0.05 and its extremes.
- 14 records at 21/53 across the calibration arms.
- 36 of 45 luna records TRUNCATED, with the 9 untruncated all at 53/53.
- REC:1 everywhere, before repeats.
- The nine-cell matrix values and the FILL OFF TARGET caveat.
- `_anchored.py` having no record concept before the fix, and the run-38 trim being real.
- The 16,617-tokens-in-3-messages arithmetic, for run 38, which is where it came from.
- Preserved-message termination: the shed loop is bounded and no caller treats False as "fits".
- The run-37 revert discipline, and refusing to retry a wording change without a new reason.

## Fixed, 6 September

Findings 1-5 are repaired; 461 tests pass, up from 443, and every fix was mutation-tested (nine
mutations, all caught). Verified independently:

    case 1  bare-value record against code_N=VALUE : 3/3 -> COVERED   (was 0/3)
    case 2  group holding 2026 and 1234            : 0/2 -> KEPT      (was DROPPED)
    thresholds                                     : 0.6 / 0.9

- The tokeniser keeps the value side of `key=value` and splits on quotes, commas and brackets, so
  JSON and CSV work. `:` is deliberately not a separator, because timestamps are built from it.
  Emitting both halves of a pair would have been worse than the bug: the eight labels join the
  eight values in the denominator, a perfect record scores 0.5, and nothing is ever dropped.
- Coverage compares token sets, so a value that is merely a substring no longer counts. The name
  rule counts whole tokens.
- `_drop_before` reads every record at or before the anchor.
- One trigger now forces one call. This also repaired an attribution that was only ever right
  *because* of the doubling: with the surplus force gone, the record surfacing on the next call
  would have been counted as the model volunteering rather than the mechanism working.
- `RECFALLBACK` counts effects. `groups_kept_uncovered` describes the current pass.
- Fixtures now render `code_N=VALUE`, so a test can no longer pass while the live check scores
  zero. The lab's own fixture calls the real `render_codes()`.

**`trigger_fraction` reverted to 0.6 and `fallback_fraction` to 0.9**, following finding 6. This
also restores the configuration every archived run used, so the next measurement is comparable
with the archive rather than a fourth untested variant. Four threshold-derived test constants
moved back; at 19,000 with 0.6/0.9 the fixture would have sat at 90.2%, *past* the give-up line,
measuring the fallback instead of the strategy.

**Every `UNCOVERED`, `RECFALLBACK` and `RECORDS` figure in runs 38 and 39 is void, not merely
noisy.** They were produced by all four defects at once. Nothing in the archive should be read on
those columns.

**Not fixed, and not fixable in the middleware:** forcing the recall tool necessarily overwrites
the run's pinned tool choice on that call. The doubling fix halves it, from two hijacked calls per
trigger to one. Removing it entirely is a runner-side decision -- skip or re-issue the lookup on a
hijacked seeding turn.
